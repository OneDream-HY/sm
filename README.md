# One Dream Community · Client e-sign (repo `sm`)

Lets **self-managed participants and partners sign the Service Agreement and the
onboarding forms from a link — no Microsoft 365 account, no login.**
When they submit, the signed PDF is:

1. filed in SharePoint in the client's own folder (`ODC Home Care  Clients › <client> › 01_Onboarding…`, matched by name the same way the coordinator apps do); if no single folder matches, it goes to `Service Agreement Records › Client Signed › <Participant>` and the e-mail says so,
2. e-mailed from `agedcare@onedreamcommunity.com.au` to the participant, the team mailbox and the coordinator,
3. logged (who / when / IP / file hash) in a Supabase table.

The existing coordinator apps (`onedream-hy/contract-client`, `onedream-hy/onboarding_new`)
are **not touched**. This repo contains copies of their pages with the
login/SharePoint parts removed and an e-sign overlay added, generated by `tools/build.py`.

## 1. How it works

```
Coordinator (any browser)                      Participant (phone / tablet / PC)
┌──────────────────────────────┐              ┌──────────────────────────────┐
│ contract/  or  onboarding/   │              │ same page, #sid=<uuid>       │
│ fill in details, staff sig   │              │ documents are READ-ONLY       │
│ ✉️ Create client link (+PIN) │              │ draws signature, places it    │
└──────────────┬───────────────┘              │ 📤 Submit → PDF built in-page │
               │ create                       └──────────────┬───────────────┘
               ▼                                             │ submit (multipart PDF)
      Supabase Edge Function  sign-session  ◄────────────────┘
               │  (service role: sign_sessions table)
               ▼  Microsoft Graph, application permissions (client credentials)
      SharePoint upload session  +  draft e-mail with attachments → send as agedcare@
```

* The participant never sees a login screen. The link holds only a session id; the
  prepared form data lives in `sign_sessions.payload` (Supabase, Sydney region if you
  chose it) and the PDFs go straight to SharePoint — nothing is kept in Supabase Storage.
* A link can be **submitted once** and expires after **30 days** (`LINK_DAYS`).
* Clause 24.2 of the Service Agreement already permits electronic signature / acceptance
  via a platform; the audit trail (timestamp, IP, user agent, SHA-256 of each PDF,
  the full snapshot of the signed form) is stored in `sign_sessions`.

## 2. Microsoft Entra app registration (one-off, admin)

1. **Entra admin center → App registrations → New registration**
   * Name `ODC Client e-Sign Service` · Single tenant · no redirect URI.
2. **Certificates & secrets → New client secret** (24 months). Copy the *value* now.
3. **API permissions → Add → Microsoft Graph → Application permissions**:
   * `Mail.ReadWrite` and `Mail.Send` (needed to create a draft with large attachments and send it)
   * `Sites.ReadWrite.All` — simplest. (Hardened alternative: `Sites.Selected`, then grant the
     app `write` on the AgedCareTeam622 site with `POST /sites/{site-id}/permissions`.)
   * Click **Grant admin consent**.
4. Note the **Application (client) ID**. Tenant ID is `857e6685-dad1-41ac-b637-b3fa089eeea8`
   (same tenant the coordinator apps use).
5. **Restrict the app to the team mailbox** (recommended; Exchange Online PowerShell):
   ```powershell
   Connect-ExchangeOnline
   New-ApplicationAccessPolicy -AppId <client-id> -PolicyScopeGroupId agedcare@onedreamcommunity.com.au -AccessRight RestrictAccess -Description "ODC client e-sign: agedcare mailbox only"
   Test-ApplicationAccessPolicy -AppId <client-id> -Identity agedcare@onedreamcommunity.com.au
   ```

## 3. Supabase (table, function, secrets)

```bash
npm i -g supabase            # or brew install supabase/tap/supabase
supabase login
supabase link --project-ref <your-project-ref>
supabase db push             # creates public.sign_sessions (supabase/migrations)

supabase secrets set \
  MS_TENANT_ID=857e6685-dad1-41ac-b637-b3fa089eeea8 \
  MS_CLIENT_ID=<client-id> \
  MS_CLIENT_SECRET='<secret value>' \
  COORDINATOR_PIN='<choose a PIN coordinators will type>' \
  ALLOWED_ORIGINS=https://onedream-hy.github.io
  # optional overrides (defaults shown):
  # SP_HOST=onedreamcommunity.sharepoint.com SP_SITE_PATH=/sites/AgedCareTeam622
  # SP_FOLDER="Service Agreement Records/Client Signed"   (fallback)
  # CLIENT_LIBRARY="ODC Home Care  Clients"   (client folders; note the double space)
  # MAIL_FROM=agedcare@onedreamcommunity.com.au MAIL_TEAM=agedcare@onedreamcommunity.com.au
  # COORDINATOR_DOMAIN=onedreamcommunity.com.au LINK_DAYS=30 MAX_FILE_MB=25 OFFICE_PHONE="02 9161 7567"

supabase functions deploy sign-session --no-verify-jwt
# → https://<project-ref>.supabase.co/functions/v1/sign-session
```

Quick smoke test from a terminal (expects `403 Incorrect coordinator PIN`):
```bash
curl -s -X POST https://<ref>.supabase.co/functions/v1/sign-session -H 'content-type: application/json' \
  -d '{"action":"create","pin":"x","page":"contract","coordinatorEmail":"a@onedreamcommunity.com.au","participantName":"T","payload":{}}'
```

## 4. Publish the pages (GitHub Pages)

1. Edit `sign/config.js` → `functionUrl: 'https://<project-ref>.supabase.co/functions/v1/sign-session'`.
2. Create the repo `onedream-hy/sm` (public, like the other two), push `main`.
3. Repo **Settings → Pages → Source: Deploy from branch · main · / (root)**.
4. Staff entry points:
   * `https://onedream-hy.github.io/sm/contract/`
   * `https://onedream-hy.github.io/sm/onboarding/`

The pages are public but hold **no client data** — a participant's documents only exist
behind their own `#sid=` link.

## 5. Day-to-day use

### Option A — one fixed link, the participant does everything (simplest)
Send the participant this link (no PIN, no preparation):

* Service Agreement: `https://onedream-hy.github.io/sm/contract/?self`
* Onboarding forms:  `https://onedream-hy.github.io/sm/onboarding/?self`

They fill in their details, draw and place their signature, and press **Submit**. The signed PDF is
e-mailed to them and to `agedcare@`, and filed in their SharePoint folder (matched by the name they
typed; otherwise *Client Signed* with a note in the e-mail). Staff signature lines stay blank for ODC
to countersign. Progress is kept on their device until they submit.

### Option B — coordinator prepares the documents first (coordinators)

1. Open `contract/` or `onboarding/`. It is the same form you know, minus the SharePoint buttons.
2. Enter the participant's details, choose the variant / tick the forms, and — if a staff
   signature is required on the documents — draw it and **Apply Signature to ALL Fields**
   (contract) or sign the staff boxes (onboarding). Type anything that must appear in the
   document (Key Terms, bank details, prices) now: the participant cannot edit, only sign.
3. **✉️ Create client link** → enter the participant's e-mail (they get the signed copy),
   your e-mail and the coordinator PIN → **Create link** → *Copy link* or *E-mail to participant*
   (opens Outlook with a ready-made message). *Preview as participant* shows exactly what they see.
4. The participant opens the link, draws their signature (or a representative/attorney draws
   theirs in the second box), places it, and presses **Submit**. Everyone receives the PDF by
   e-mail within a minute; the file is in SharePoint under *Client Signed › Participant name*.

Things to know
* One link = one submission. For a correction, create a new link.
* Staff signature fields are locked on the participant side; consent / do-not-consent
  boxes are signed individually (never by "apply to all").
* If the function URL is wrong or the service is down, the participant sees a clear
  error with the office phone number; nothing is lost on their side until they submit.

## 6. Keeping the copies up to date

When `contract-client` or `onboarding_new` changes, regenerate (never edit `contract/index.html`
or `onboarding/index.html` by hand):

```bash
git clone --depth 1 https://github.com/onedream-hy/contract-client ../contract-client
git clone --depth 1 https://github.com/onedream-hy/onboarding_new ../onboarding_new
python3 tools/build.py --contract ../contract-client/index.html --onboarding ../onboarding_new/index.html
```

`tools/build.py` asserts every edit; if the upstream page changes shape it stops with a
message instead of producing a broken page.
